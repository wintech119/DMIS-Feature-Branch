Part A – OS Access Violations

Step A1 – Find risky file/system operations
Search for:

Any file path manipulation that uses request parameters or user input (open(...), os.path.join, os.remove, path passed into other functions).

Any usage of ../ style patterns or direct concatenation of paths.

For each case, determine whether a user can influence the path or filename, directly or indirectly (e.g. through DB values).

Step A2 – Prevent directory traversal & unsafe paths
For user-influenced file operations:

Restrict operations to a specific base directory (e.g. an uploads or reports folder configured in settings).

Normalize paths and assert they stay inside the base directory. For example:

import os  

BASE_DIR = app.config.get("SAFE_STORAGE_DIR")  

def safe_join(base, *paths):  
    final_path = os.path.abspath(os.path.join(base, *paths))  
    if not final_path.startswith(os.path.abspath(base) + os.sep):  
        raise ValueError("Attempted directory traversal")  
    return final_path  


Replace any direct concatenation like:

file_path = "/some/base/" + user_filename  


with:

file_path = safe_join(BASE_DIR, user_filename)  


Add validation for filenames (e.g. allow only alphanumeric + limited safe chars, no path separators).

Step A3 – Preserve functional output

Ensure any report generation, export, or file download features still work the same, but now operate only on safe paths.

Part B – Insufficiently Protected Credentials

Step B1 – Search for credential handling
Search the code base for:

password, pass, secret, token, api_key, key, credential.

Any hardcoded secrets in Python files or templates.

Any place where passwords or secrets might be logged (logger.info(...), print(...)).

Step B2 – Fix storage and handling
For any issues you find:

Ensure user passwords are never logged or stored in plain text.

Confirm passwords are only stored as strong cryptographic hashes (e.g. using Werkzeug/Flask generate_password_hash / check_password_hash or similar).

Move any hardcoded secrets (API keys, tokens) into environment variables or a separate configuration, not committed into code.

Mask or omit credentials from logs and error messages.

Example changes:

Before (bad):

logger.info("User %s logged in with password %s", username, password)  


After (good):

logger.info("User %s attempted login", username)  


Step B3 – Confirm no downgrade of existing security

Keep the existing authentication and password hashing approach, unless you are upgrading it to a stronger, backwards-compatible option.

When done, provide:

A list of locations where OS access risks were mitigated (with before/after snippets).

A list of locations where credential handling/logging was improved.
